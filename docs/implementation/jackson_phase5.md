# Jackson — Phase 5 backend, persistence and deployment

This contribution implements Jackson's backend scope against specification 3.0.0 and ruleset 2.0.0. The supplied ZIP and its shared files were read without modification; a scratch extraction under `/tmp` passed its hash/schema/example/vector validator (59 definitions, 26 examples, 21 negatives, 435 assertion inventory entries). The pack is an implementation target, not evidence of pod adoption or passing hosted acceptance. Audit rules, finding identities, correction behavior, independent tester expectations and historical report bytes remain governed by their existing contracts.

## Backend interfaces and behavior

`LifecycleService` exposes `get_schedule`, `configure_schedule`, `get_notifications`, `delete_workbook`, `authorize_clock`, `advance_clock`, `tick` and `recover_deletions`. Schedule GET/PUT, notification GET and owner DELETE are registered with strict parsing, resource/session authorization, ProjectError responses, request IDs and OpenAPI schemas. Ryan owns the HTTP clock route and UI; no clock route or UI was added by this contribution.

Ryan's clock handler should check trusted `settings.enable_test_clock` and presence of `X-Test-Session` first (404 TEST_CLOCK_DISABLED), then authenticate through `auth_service.require_test_admin`. Validate the supplied session identifier and call `authorize_clock` before reading the bounded JSON body. Pass the creating test-admin principal, session header and parsed object to `advance_clock`. Return its serialized `ClockResponse`; use the normal project error handler. `ProjectService.check_session` deliberately rejects test-admin business access and is not the clock authentication path. `advance_clock` also checks ownership/readiness inside its transaction. No clock, owner or namespace may come from ordinary business request JSON.

Fresh setup with ENABLE_TEST_CLOCK=true stores the default 2027-01-01T00:00:00Z clock, or strict setup.clock.currentTime, atomically with session creation. Existing sessions retain their absent clock and return LEGACY_SESSION_CLOCK. Fault controls use the existing trusted ENABLE_TEST_AUDIT_FAULTS switch; all seven Phase 5 one-shot counters are accepted only during new isolated setup. Explicit clock/fault controls when disabled fail before session creation or cleanup. No counter can be rearmed by reusing a session ID.

Schedule replacement validates strict integer intervals 1–90, actual calendar dates and unknown/duplicate fields. First enable and interval changes reset cadence; deadline-only and identical requests preserve it. The latest version is selected from the durable version creation sequence, including generated versions; re-audit order never changes selection. Due work is coalesced on its original interval grid. Audit acceptance, cadence, reminder consideration/deduplication and isolated clock advancement share one BEGIN IMMEDIATE transaction. Busy due versions reject a clock advance without changes; ordinary ticks leave them due. The 1,000 audit/3,000 occurrence clock limits and calendar overflow checks precede mutation.

Reminder eligibility uses the newest version's latest audit before any dispatch in that transaction. Successful clean snapshots suppress durably considered keys; processing, failed, absent or unresolved snapshots remain eligible. UTC midnight calendar offsets are 90/30/7 days. Configuration does not backfill elapsed thresholds; exact-time thresholds remain eligible. Notification records are terminal, persisted and ordered by threshold then creation sequence. Deadline changes do not erase earlier records or deduplication keys.

Business acceptance and completion times use the namespace's effective time, inside persistence transactions. Queue deadlines, worker leases, timeouts, protection leases and suite budgets use real UTC/monotonic time. Completion cannot precede acceptance. New report snapshots identify specification 3.0.0 and report format 2.0.0. Migration and retrieval do not relabel retained Phase 4 snapshots.

## Deletion and retained copies

DELETE serializes against workbook storage writes using an OS file lock shared by API/worker processes on the same persistent metadata directory. Immutable upload writes and generated candidate publication hold this lock; SQLite rechecks deletion fences before accepting operations. Active jobs or unexpired upload staging reject deletion. Stale jobs are fenced through the existing recovery machinery. An expired writer still performing external I/O holds the storage lock, preventing premature success. This deployment supports one host and one shared SQLite/storage-lock directory, not independent hosts with unrelated lock files.

A committed deletion reservation hides all ordinary workbook/version/audit/remediation/output/schedule/notification/history access. The original owner can retry DELETE; other identities cannot inspect the cleanup reservation. The worker housekeeper also resumes one pending cleanup per pass. The injected pre-delete failure consumes its isolated fault without reserving or removing content, leaving the workbook readable.

Cleanup removes the entire exact workbook storage subtree/prefix, including generated and abandoned candidates. S3 cleanup enumerates and permanently removes every version and delete marker, checks per-object errors, then verifies the prefix is empty. This follows the [S3 version-deletion contract](https://docs.aws.amazon.com/AmazonS3/latest/userguide/DeletingObjectVersions.html) and [DeleteObjects response semantics](https://docs.aws.amazon.com/AmazonS3/latest/API/API_DeleteObjects.html). Filesystem cleanup also removes temporary files in that subtree. Registered backup blob roots receive the same removal. Metadata erasure covers jobs, findings/review/report snapshots, versions, history, decisions, idempotency, outputs, schedules, reminders, notification records and staging/cleanup rows. SQLite secure_delete, VACUUM and WAL truncation remove retained freed-page/WAL content before success; failure leaves the reservation recoverable. An API deadline returns DELETION_FAILED if cleanup is still running; storage fencing remains held by that cleanup.

`system.sqlite3.deletions` is an independent, content-free SQLite journal containing only opaque workbook IDs. Never replace or roll it back with a content backup. Startup uses it to fence workbooks restored from older metadata before normal access; journal replay failure blocks metadata access rather than serving restored content. Recovery purges restored content. The main database retains opaque deleted IDs to reject late recreation. Session cleanup removes its simulated time, counters and scheduling/notification state, without deleting independent tester reports.

All retained application-managed copies must be registered through MANAGED_METADATA_BACKUPS, MANAGED_METADATA_BACKUP_ROOT and MANAGED_BLOB_BACKUPS. Missing/unwritable configured copies make deletion fail; they cannot be silently ignored. The production deployment backup routine moves earlier deployment system databases into the registered `deletion-backups/<release>/system.sqlite3` tree and creates subsequent copies there. Private compose credentials and independent tester reports stay in the host-only backup tree. Both API and worker mount only the system content backup tree for deletion. Operator-created off-host copies, replication destinations, exports and EBS snapshots require an explicit purge procedure before enabling owner deletion; they are not covered by merely configuring the live database. Do not retain unregistered content copies or restore them into service. Provider forensic remnants are outside this prototype's physical-erasure claim.

## Rollout and restore

1. Stop ingress and both metadata writers through the deployment drain procedure. Preserve the current deletion journal separately from content backups. Schema migration 2 → 3 is additive, transactional and idempotent; schema 1 still upgrades through schema 2. Earlier payloads/reports remain unchanged. Phase 4 binaries refuse schema 3.
2. Inventory existing local/off-host system database copies, blob copies, replication and snapshots. Move/register writable copies and remove unsupported retained content copies. The deployment script handles its own earlier local system backups; other copies require operator action. Ensure mounted backup directories and files are owned by the system database UID/GID (production 10001), without exposing compose credentials.
3. Review S3 permissions before activation. The current Phase 4 IAM template lacks version-listing and version-deletion permissions. Generate a baseline from the adapter with `DISABLE_IAM_POLICY_AUTOPILOT_TELEMETRY=true uvx iam-policy-autopilot@latest generate-policies app/storage/blobs.py --language python --service-hints s3 --pretty`. This command was executed locally with analyzer 0.4.0; it does not apply policies. Review and scope its output to the existing bucket/sources prefix. Required additions are s3:ListBucketVersions on the bucket and s3:DeleteObjectVersion on retained source objects, alongside existing IO/delete access. The analyzer's broader optional KMS/retention/ACL/Object Lambda permissions are not needed for the configured AES256, ordinary S3 adapter. Do not grant retention bypass. Object Lock/MFA deletion restrictions must cause controlled failure, not a false 204. Actual role changes and live S3 deletion remain deployment verification tasks.
4. Deploy compatible API and worker images together. Keep worker --concurrency 2. Enable clock/fault capabilities only on the designated isolated test deployment. Ordinary production can keep both disabled. Deployment protection is 2,700 real seconds, renewed by business activity when fewer than 2,400 remain, and by successful clock advances. The proxy uses 2,700 seconds; registered Phase 5 callers need at least 2,430. Tester process allowance is 2,400, without relabeling the existing Phase 4 manifest. The release probe accepts the actual Phase 4 profile or a future real Phase 5 profile; Dixon must supply the Phase 5 executable suite. The deploy poll process allows both drain windows and build overhead; a protected evaluation causes deferral on drain timeout.
5. Verify health, real schedule dispatch, isolated-clock integration, complete deletion and failed cleanup recovery on the deployment host. Test an actual versioned S3 prefix and configured backup copies. No live migration, permissions change, deployment or hosted suite was performed here.

For restore, stop ingress/API/worker, restore the selected content database and blobs, and carry forward the newest independent deletion journal. Run the Phase 5 migration/fence replay before opening ingress; allow cleanup recovery to purge fenced restored content, and verify deleted URLs stay 404. Do not restore an older journal or run a Phase 4 binary after any Phase 5 acknowledged deletion. Independently retained tester reports are restored by their own policy and are not workbook artifacts. Rehearse this procedure on an isolated copy before claiming backup/restore acceptance.

## Monitoring and response

The worker uses two execution slots, an independent object-cleanup housekeeper and a dedicated one-second scheduler thread. Scheduler transactions never perform object-store I/O. Real scheduler passes exclude every test namespace. Stop signals stop future scheduling/claims and drain accepted execution. The final stopped-writer deployment recheck includes pending deletion reservations as well as audits, remediations, staging and protected external sessions.

Content-safe JSON events include scheduled_audit_accepted with scheduler/audit/workbook/session IDs and dispatchLag; terminal job_finished with code/stage/duration; notification_recorded with DELIVERED/FAILED; scheduler_tick_failed; workbook_deletion_failed and deletion_recovery_pending. backend_monitor emits queueDepth, failedJobs, notificationFailures and pendingDeletions every 30 seconds. No workbook contents, tokens or exception text are included. This is a concrete structured-log signal, not an assertion that CloudWatch alarms have been installed.

If dispatchLag exceeds five seconds while dependencies are healthy, or scheduler_tick_failed appears, check worker liveness, SQLite contention and engine compatibility. If queueDepth grows or failedJobs rises, inspect job_finished stages: queue timeout differs from engine/worker failure; preserve the 15/60/180-second bounds and coordinate concurrent suites rather than extending them. Investigate FAILED notifications without retrying the same occurrence. For pending deletion, repair the missing storage/backup permission or dependency and let recovery (or the original owner's DELETE) continue. Never remove a reservation or journal to force apparent success. A local two-process integration check demonstrates a single scheduled claim, structured monitor events and graceful draining; notification fault and partial-storage deletion checks demonstrate their failure signals. Hosted alarm routing and an actual operator response remain operational evidence to collect.
